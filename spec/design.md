# Estate Patrol Service — Design

Plantation estate & tree registry with drone patrol distance planning.
Stack is fixed by the assignment: Go 1.21, Echo, oapi-codegen, PostgreSQL, GoMock, Make, Docker Compose.

---

## 1. Goals and constraints

| Constraint | Consequence for the design |
|---|---|
| Estate up to 50,000 × 50,000 = **2.5 × 10⁹ plots** | Nothing may be O(plots). No grid allocation, no plot loop. Everything is O(trees). |
| Max distance ≈ 10 × 2.5 × 10⁹ = 2.5 × 10¹⁰ m | Distance math in `int64`; OpenAPI `format: int64`. |
| "One tree per plot" | Enforced by a DB unique constraint, not an application check (race-free). |
| OpenAPI is the backend↔app contract; generated code **must** be used | `api.yml` is the source of truth for shapes *and* schema-level validation. |
| Graded automatically via `run.sh` on Go 1.21 / Ubuntu or macOS | Stay on Go 1.21; startup must tolerate DB not being ready yet. |
| ≥ 70% unit coverage | Core logic lives in pure, dependency-free packages. |

## 2. Architecture

```
            HTTP
             │
   ┌─────────▼──────────┐   Echo middlewares: Recover → RequestID → Logger → BodyLimit
   │  OpenAPI validator │   → OapiRequestValidator (schema: types, required, min/max, uuid)
   └─────────┬──────────┘
   ┌─────────▼──────────┐   implements generated.ServerInterface
   │      handler/      │   semantic validation (plot within estate), error → HTTP mapping
   └───┬────────────┬───┘
       │            │ pure function calls
       │     ┌──────▼───────────────┐
       │     │ droneplan/ treestats/│  no I/O, no Echo, no SQL — fully table-tested
       │     └──────────────────────┘
   ┌───▼────────────────┐
   │   repository/      │  RepositoryInterface (gomock) + Postgres impl
   └───┬────────────────┘  maps pq errors → domain errors (ErrNotFound, ErrPlotOccupied)
       ▼
   PostgreSQL
```

**Packages**

| Package | Responsibility |
|---|---|
| `cmd/` | Config from env, DB connect with retry, middleware wiring, server timeouts, graceful shutdown. |
| `generated/` | oapi-codegen output (types, server, embedded spec). Never hand-edited. |
| `handler/` | Bind → semantic validation → repository → pure computation → response. Owns the HTTP error handler. |
| `repository/` | SQL only. Returns domain errors, never `pq` errors. |
| `droneplan/` | Patrol distance and forced-landing point. Pure functions over `(length, width, []Tree)`. |
| `treestats/` | Count / min / max / median from a height histogram. Pure. |

### Decision: no service layer
- **Chosen:** handler → repository, with domain logic in pure packages called by the handler.
- **Rejected:** a `service/` layer with its own interface + mocks. It would be a pass-through with no behavior of its own: one more mock layer, more indirection, no testability gain (the logic is already pure). It also diverges from the starter project's structure, and "adapting to our standards" is explicitly graded.
- **Revisit when:** a use case spans multiple repositories or needs a transaction boundary.

### Decision: schema validation in OpenAPI middleware, semantic validation in handler
- **Chosen:** constraints (`minimum`, `maximum`, `required`, `format: uuid`, `type: integer`) are declared in `api.yml` and enforced by kin-openapi's request validator. The handler only checks rules that need data: plot inside estate bounds, plot not occupied.
- **Why:** the spec is the contract consumed by the apps team. Declaring constraints there documents them for clients *and* enforces them, from one source. It also correctly rejects an **empty body** (Echo's binder silently binds nothing when `Content-Length: 0`), `10.5`, and `"10"`.
- **Rejected:** validating everything in handlers. That duplicates the spec and lets the two drift apart.
- **Cost:** handler unit tests assume schema-valid input. Schema rejection paths are covered by API tests instead. Validator error text is reformatted by our error handler so responses stay `{message}`.

## 3. Data model

PostgreSQL 14. Singular `snake_case` table names. UUIDv4 keys generated by the DB (`gen_random_uuid()`, built in since PG 13) and returned via `RETURNING`.

### `estate`
| Column | Type | Constraints |
|---|---|---|
| `id` | `uuid` | PK, default `gen_random_uuid()` |
| `length` | `integer` | NOT NULL, CHECK 1..50000 (west→east plots) |
| `width` | `integer` | NOT NULL, CHECK 1..50000 (south→north plots) |
| `created_at` | `timestamptz` | NOT NULL, default `now()` |

### `tree`
| Column | Type | Constraints |
|---|---|---|
| `id` | `uuid` | PK, default `gen_random_uuid()` |
| `estate_id` | `uuid` | NOT NULL, FK → `estate(id)` ON DELETE CASCADE |
| `x` | `integer` | NOT NULL, CHECK ≥ 1 |
| `y` | `integer` | NOT NULL, CHECK ≥ 1 |
| `height` | `smallint` | NOT NULL, CHECK 1..30 |
| `created_at` | `timestamptz` | NOT NULL, default `now()` |

`CONSTRAINT tree_estate_plot_key UNIQUE (estate_id, x, y) INCLUDE (height)`

**Why each choice**
- **Unique `(estate_id, x, y)`** is the "one tree per plot" rule. Two concurrent inserts on the same plot give exactly one `201`, and the other fails with SQLSTATE `23505`, which becomes `400`. An app-side "check then insert" is a TOCTOU race and is rejected.
- **Leading `estate_id`** means the same index serves every per-estate query. No separate FK index is needed.
- **`INCLUDE (height)`** makes both read paths (stats: `height`; drone plan: `x, y, height`) index-only scans. It costs nothing extra to maintain because the unique index exists anyway.
- **CHECK constraints duplicate API validation on purpose.** They are the last line of defense against a bad writer (script, future endpoint).
- **`x ≤ length` is not enforced in the DB.** It is cross-table and would need a trigger. Rejected because estates are **immutable** (no update endpoint), so an app check against a freshly read estate cannot go stale. Triggers also hide business logic.
- **`smallint` for height** (range 1..30); `integer` for coordinates (50,000 > `smallint` max).
- **DB-generated UUIDs over app-generated:** one round trip with `RETURNING`, and there is no client-side retry or idempotency need that app-side IDs would serve.

## 4. API contract

All errors: `{"message": string}` with an appropriate status. Unknown routes also return JSON. `/hello` is removed.

| Method & path | Request | Success | Errors |
|---|---|---|---|
| `POST /estate` | `{length: int 1..50000, width: int 1..50000}` | `201 {id: uuid}` | `400` invalid/missing/non-integer |
| `POST /estate/{id}/tree` | `{x: int ≥1, y: int ≥1, height: int 1..30}` | `201 {id: uuid}` | `400` malformed id / invalid body / out of bounds / plot occupied; `404` estate not found |
| `GET /estate/{id}/stats` | – | `200 {count: int64, min: int, max: int, median: number}` | `400` malformed id; `404` not found |
| `GET /estate/{id}/drone-plan` | `?max_distance=int64 ≥1` (optional) | `200 {distance: int64, rest?: {x: int, y: int}}` | `400` malformed id / bad `max_distance`; `404` not found |

- `x`/`y` also declare `maximum: 50000` in the spec so obviously-invalid input is rejected early. The estate-specific bound is checked in the handler.
- `rest` is present **only** when `max_distance` is supplied (additive field; the base contract is unchanged).
- Unknown JSON fields are **accepted and ignored** (see §8).

## 5. Algorithms

### 5.1 Patrol path as a 1-D sequence

Total plots `N = L·W`. The serpentine path visits plot index `p ∈ [0, N)`:

- row `r = p / L`, offset `o = p mod L`
- `y = r + 1`; `x = o + 1` if `r` is even (eastbound), else `L − o` (westbound)
- inverse: `p(x, y) = (y−1)·L + (x−1)` if `y` odd, else `(y−1)·L + (L−x)`

Every consecutive pair of plots is exactly 10 m apart, **including the northward turn**. This is what makes the problem 1-D.

### 5.2 Total distance

Monitoring altitude `a(p) = h(p) + 1`, with `h = 0` for an empty plot.

```
distance = 10·(N−1)                      horizontal
         + a(0)                          take-off from ground
         + Σ |a(p+1) − a(p)|              climbs and descents between plots
         + a(N−1)                        final landing
```

Crash avoidance and minimum pivoting: climb *before* moving when the next plot is higher, move *then* descend when it is lower. This matches the PDF diagram. It changes the **order** of segments, not their sum, so it only matters for §5.3.

**O(T log T) evaluation.** Load the estate's trees, compute `p` for each, and sort by `p`. Walk the sorted trees, keeping the previous tree's `p` and altitude:
- adjacent (`p = prev+1`): add `|a − a_prev|`
- gap of ≥1 empty plot: add `(a_prev − 1) + (a − 1)` = `h_prev + h`, because the drone drops to 1 m over the empty run and rises again
- the start and end are handled as virtual empty neighbours at altitude 1, plus the 1 m take-off and 1 m landing.

Sorting in Go (not `ORDER BY` in SQL) keeps all path knowledge in one tested package.

**Worked checks** (these become test cases):

| Estate | Trees | Expected |
|---|---|---|
| 5×1 | (2,1)=5, (3,1)=3, (4,1)=4 | 54 (PDF: 40 H + 14 V) |
| 5×1 | (2,1)=10, (3,1)=20, (4,1)=10 | 82 (starter test) |
| 1×1 | none | 2 |
| 1×1 | (1,1)=h | 2h + 2 |
| L×W | none | 10·(LW−1) + 2 |
| 50000×50000 | 3 trees | exact value, < 10 ms |
| 3×2 | (3,1), (3,2) | row-turn adjacency: treated as adjacent |

### 5.3 BONUS: forced-landing point (`rest`)

Model the flight as an ordered list of segments, each attributed to a plot:

| Segment | Landing plot if the battery runs out **during** it |
|---|---|
| take-off / climb at plot `p` (before moving) | `p` |
| horizontal `p → p+1` | `p` (the last plot reached) |
| descent at `p+1` (after moving) | `p+1` |

When the budget runs out **exactly** at the end of a segment, the drone is at that segment's end plot. If `max_distance ≥ distance`, `rest` = the last plot of the path.

**O(T)** after the sort: walk the same tree-sorted sequence and consume the budget segment by segment. Runs of empty plots are pure 10 m hops at 1 m altitude, so when the budget ends inside a run, jump ahead `⌊remaining/10⌋` plots arithmetically. Then convert `p → (x, y)` with §5.1.

The forced-landing descent itself **does not count** against `max_distance`. The spec says it uses the *backup* battery, and `max_distance` budgets the main battery only.

### 5.4 Stats

Query `SELECT height, count(*) … GROUP BY height`. Heights are 1..30, so this returns **≤ 30 rows** whatever the tree count. `treestats` derives count, min, max, and median from that histogram in O(30).
- Median is exact: the average of the two middle values for an even count (e.g. 3 and 4 → `3.5`).
- An empty estate returns all zeros, per spec.
- **Rejected:** `percentile_cont` in SQL. It is correct, but it puts logic into SQL where it is harder to unit test, and it transfers nothing less.
- **Rejected (for now):** a denormalized per-estate histogram maintained on insert. It is O(1) reads, but it adds write contention on a hot estate row and a consistency burden. This is the scale path if stats become hot.

## 6. Error handling

- The repository translates driver errors into domain errors:
  - `sql.ErrNoRows` → `ErrNotFound`
  - `23505` (unique violation) → `ErrPlotOccupied`
  - `23503` (FK violation) → `ErrNotFound` (defensive)
- The handler maps domain errors to HTTP:
  - `ErrNotFound` → 404
  - `ErrPlotOccupied` / `ErrOutOfBounds` → 400
  - anything else → 500
- A custom `echo.HTTPErrorHandler` guarantees every error body is `{message}`.
  - 500s return a generic message. The real error is logged with the request ID and never leaked.
  - Validator messages are shortened to a stable, client-readable form.
- A malformed path UUID gives `400`, not `404`. The request is syntactically invalid, and no resource lookup happens. (The generated binder behaves this way already.)

## 7. Operability & failure modes

**Runtime hygiene (cheap, included):**
- Recover, RequestID, and request-logging middleware.
- `BodyLimit` (a few KB), so an oversized body gets `413`.
- `http.Server` read/write/idle timeouts. Every query uses the request `context`.
- `sql.DB` pool limits set explicitly.
- Graceful shutdown on SIGINT/SIGTERM that drains in-flight requests.
- Config from env (`DATABASE_URL`, port), with defaults matching compose.

| Failure | Behavior |
|---|---|
| Postgres not ready at startup | Ping with bounded retry and backoff (~30 s), then exit non-zero. Compose sets `restart: on-failure`. The DB healthcheck uses `pg_isready -h localhost`: without `-h`, it checks the Unix socket and can report ready while init scripts are still running. |
| DB lost mid-request | 500 `{message}`; error logged with request ID. |
| Concurrent insert on the same plot | Exactly one 201; the rest get 400 (unique constraint). |
| Huge estate, few trees | O(T) algorithms; no grid allocated. |
| Estate with very many trees | Drone-plan loads `(x, y, height)` for all trees: about 24 B each, so 1 M trees ≈ 24 MB. Acceptable here. Streaming rows in path order is the upgrade path. |
| Distance overflow | `int64` end to end. |

**Observability, deliberately minimal:** structured request logs with request ID, method, path, status, and latency. No metrics or tracing (see §9).

### 7.1 Build & test reproducibility

The grader runs `run.sh` cold on Go 1.21 (Ubuntu/macOS). Development happens on Windows, so the build is pinned so that it cannot drift.

| Decision | Why |
|---|---|
| Build and test with the **Go 1.21.13 toolchain** (`GOTOOLCHAIN=go1.21.13`), not the newer host Go; final `run.sh` dry run under WSL2 | `go 1.21` in `go.mod` blocks newer *language* features but not newer *stdlib* APIs (`slices.Concat`, `cmp.Or`, …). Only a 1.21 toolchain catches those before the grader does. The WSL dry run shows the POSIX scripts behave the same way they will on the grader's Ubuntu/macOS. |
| Mocks use **`go.uber.org/mock` v0.4.0** (not `github.com/golang/mock`) | The README tells the grader to install `go.uber.org/mock/mockgen`. If `make init` regenerates a mock, it imports `go.uber.org/mock/gomock`, and tests written against `golang/mock` stop compiling. `golang/mock` is also archived. v0.4.0 is pinned because later versions need Go ≥ 1.22. |
| Tool versions pinned in README (`oapi-codegen` v1.16.3, `mockgen` v0.4.0) | `@latest` can change what code gets generated between the day I build it and the day it is graded. |
| `.gitattributes` forces LF | With `core.autocrlf=true` on Windows, `run.sh` could pick up CRLF endings and fail on Linux with `bash\r: No such file`. |
| Unit coverage **excludes `generated/` and `*.mock.gen.go`** | Machine-generated code is not the code under test. Including it lowers the number without saying anything about test quality. The exclusion is done in the Makefile and stated in the README, not hidden. |

## 8. Assumptions (spec ambiguities, resolved without clarification)

| # | Ambiguity | Assumption | Reason |
|---|---|---|---|
| A1 | PDF says create returns **201**; starter test asserts 200 | **201**. The local test is updated. **Highest-risk assumption.** | The written spec is the contract, and 201 Created is the correct REST semantics. |
| A2 | Bonus param: `max_distance` / `max-distance` / `distance` | `max_distance` | Section heading of the spec; snake_case matches the rest of the API. |
| A3 | Invalid `max_distance` → "404 Bad Request" | **400** | 404 is Not Found. The text says "Bad Request", which is 400. |
| A4 | Median for an even count | Exact `number` (3.5) | Mathematically correct; floor or round loses information silently. |
| A5 | Bonus `distance` field | Always the **full plan distance** | A field's meaning must not change because a query parameter is present. The distance flown is `min(distance, max_distance)`, which clients can compute. |
| A6 | Landing plot mid-segment | §5.3 table | Follows the climb-before-move / descend-after-move flight order in the PDF diagram. Consistent with the example output (`distance: 100`, `rest (10,1)`). |
| A7 | Does the landing descent count toward `max_distance`? | No | The spec: the forced landing uses the backup battery. |
| A8 | Malformed UUID | 400 | Syntactically invalid request; matches generated binder behavior. |
| A9 | `10.5`, `"10"`, empty body, overflow | 400 | Enforced by schema validation. |
| A10 | Unknown JSON fields | Accepted and ignored | The spec is a contract with client apps. Rejecting unknown fields breaks forward compatibility when clients ship first. |
| A11 | Go 1.22 (spec stack) vs 1.21 (grader machine, `go.mod`) | Stay on **1.21** | The grader's toolchain is what has to build it. |
| A12 | `make test_unit` (spec) vs `make test` (Makefile) | Add a `test_unit` alias | Satisfies both. |
| A13 | `api.yaml` (spec) vs `api.yml` (repo) | Keep `api.yml` | The Makefile depends on it. |
| A14 | Starter `/hello` endpoint and tests | Removed | Spec defines exactly four endpoints. |
| A15 | README installs `go.uber.org/mock/mockgen`; `go.mod` and the starter mock use `github.com/golang/mock` | Switch to `go.uber.org/mock` v0.4.0 | Matches the tool the grader installs; see §7.1. |
| A16 | "≥ 70% unit coverage" doesn't define the denominator | Hand-written packages only (excludes `generated/`, mocks) | Standard practice; stated in README and Makefile. |

## 9. Deliberately not building

| Not building | Why | Where it would go |
|---|---|---|
| AuthN/AuthZ, multi-tenancy | Not in scope. Any estate ID is readable by anyone who has it. | Middleware plus an `owner_id` column. |
| List / update / delete endpoints, pagination | Not required. Immutable estates also simplify correctness (see §3). | If estates become mutable, bounds checks must move into the transaction. |
| Idempotency keys on POST | A retried `POST /estate` creates a duplicate. Acceptable for an assignment. | `Idempotency-Key` header plus a unique key table. |
| Caching drone-plan results | Computation is O(T) and cheap. Caching would need invalidation on every tree insert. | Store the computed distance per estate, invalidated on insert. |
| Metrics, tracing, `/healthz` | Operational tooling beyond what the grader runs. | Prometheus middleware, OTel, a readiness probe that pings the DB. |
| Migration tool | `database.sql` via the compose init is the mandated mechanism. | golang-migrate. |
| Rate limiting, CI | Out of scope for a single-machine assignment. | Gateway or Echo middleware; GitHub Actions running `run.sh`. |

## 10. Testing strategy

| Layer | Approach | Proves |
|---|---|---|
| `droneplan` | Table tests (§5.2 cases). A **brute-force O(N) reference simulator** (test-only) is compared against the O(T) implementation on randomized small estates, for both total distance and `rest`. | Correctness of the optimized algorithm, including every landing edge case. |
| `treestats` | Table tests: empty, single, odd, even, all-same heights. | Median semantics. |
| `handler` | gomock `RepositoryInterface` plus `httptest` and Echo. One test per status branch. | HTTP mapping and semantic validation. |
| `repository` | `go-sqlmock` for error translation (`ErrNoRows`, `23505`, `23503`). | Driver errors never leak. |
| API (`tests/`) | Extend the starter harness against the compose stack: every status code, occupied plot, out of bounds, even median, bonus cases, malformed UUID, empty body. | The real stack, including validator middleware and SQL. |

Coverage target ≥ 70% (unit), measured with `make test` over hand-written packages (generated code and mocks are excluded, see §7.1). The pure packages should be near 100%.
